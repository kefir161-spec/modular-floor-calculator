# План переработки конфигуратора (рабочее ТЗ v2)

Документ заменяет `claude_modular_floor_calculator_full_prompt.md` в качестве рабочего плана.
Исходный документ сохраняется как источник продуктовых требований заказчика.

Здесь: результаты аудита кода, изменения относительно исходного ТЗ с обоснованием,
порядок работ и измеримые критерии приёмки.

---

## 1. Результаты аудита

### 1.1. Базовое состояние — здоровое

| Проверка | Результат |
|---|---|
| `npm run typecheck` | проходит |
| `npm run lint` | 2 warning (fast-refresh, unused var в скрипте) |
| `npm run test` | 63 теста в 13 файлах, все проходят |

Архитектура FSD (`app / entities / features / pages / shared / widgets`) выдержана.
Геометрия (`shared/geometry`) отделена от UI и покрыта тестами. Адаптер каталога
изолирован интерфейсом. **Полный rewrite не нужен и не оправдан** — база пригодна
для эволюции.

### 1.2. Проблемы, найденные в коде

Ниже — только подтверждённые фактами наблюдения, они определяют порядок работ.

**Расчёт запускается на визуальные изменения.**
`setLayout` всегда вызывает `recalculate()`, а в `LayoutSettings` вместе с
геометрией (`rotation`, `offsetX/Y`, `startPoint`) лежат чисто визуальные флаги
(`showGrid`, `showDimensions`, `showCutVisualization`). Переключение галочки
«показать размеры» пересчитывает всю раскладку.
→ Требование §15.4 исходного ТЗ невыполнимо без разделения модели состояния.

**Canvas размонтируется при работе пользователя.**
`CalculatorShell.visible()` на мобильном рендерит только активный шаг, то есть
переход «Помещение → Результат» уничтожает Konva Stage и заставляет заново
грузить текстуры.
→ Прямо нарушает §15.2 и §15.3. Мобильный шаговый режим нельзя строить на
условном рендере.

**Layout зависит от JavaScript.**
`isMobile` определяется через `matchMedia` в `useEffect`, что даёт вспышку
неправильной раскладки на первом кадре.
→ §15.1 требует CSS-first. Плюс в `MobileStepper` есть дублирующий `useIsMobile`,
который вызывает `matchMedia` прямо в теле функции без подписки — он не
используется нигде и подлежит удалению.

**Zoom и pan отсутствуют как подсистема.**
Трансформация Stage вычисляется из bbox (`computeViewTransform`) на каждый рендер.
Пользовательского view-состояния нет вообще.
→ Это не «добавить кнопки», а введение новой модели вида. Делать её отдельно от
работы над canvas — значит переписывать одно и то же дважды.

**Экспорт завязан на текущий вид Stage** (`stageRef.current.toDataURL`).
После введения zoom/pan PNG и PDF начнут выгружать то, что пользователь видит на
экране, включая обрезанную приближённую схему.
→ **Риск регрессии, не отмеченный в исходном ТЗ.** Требует явного решения.

**Служебная графика внутри Konva.**
Инфо-строка «Модуль … · целых … · подрезок … · заказ …» и подложка под неё
рисуются внутри Stage и участвуют в расчёте доступной площади
(`captionPadPx`), уменьшая помещение. Легенда набрана символами `■` и `◎`.

**Undo/Redo — локальный `useState` внутри `RoomWorkspace`.**
История теряется при размонтировании компонента, начальный контур в неё не
попадает (первый «отменить» недоступен), изменения размеров прямоугольника и
перетаскивание вершин ведут историю несогласованно.
→ Этап 18 требует корректные «Отменить/Вернуть» для каждого изменения формы;
на текущей реализации это недостижимо.

**Два несинхронизированных источника цвета.**
`shared/config/theme.ts` (для Konva) и CSS-переменные в `global.scss` дублируют
палитру вручную. Любой редизайн разъедет их.

**Дизайн-токенов почти нет.**
Есть цвета, 3 радиуса, 1 тень, 5 шагов отступов. Нет z-index, motion, высот
контролов, focus ring, шкалы поверхностей, состояний hover/pressed/selected.

**UI-инфраструктуры нет.**
В `shared/ui` только `Button`, `Input`, `Card`. Drawer, Popover, BottomSheet,
Dialog, Toast, Tooltip, Skeleton, SegmentedControl, Switch, IconButton, EmptyState —
всё это предстоит создать. Это самая недооценённая часть исходного ТЗ по объёму.

**Каталог нарушает несколько требований одновременно.**
Характеристики варианта доступны только через CSS-tooltip при наведении
(`chipTooltip`); цена выводится как `от N ₽` без единицы; раскрытие групп
обозначено символами `▸ ▾`; технический ID предлагается вводить в поиск
(placeholder «Линейка, название или ID»); все линейки свёрнуты по умолчанию.

**Мёртвый код.**
`optimizeLayout` в `shared/geometry/layout.ts` определён, но не вызывается нигде.
Флаг `showGrid` хранится в состоянии и сохраняется в проектах, но сетка нигде не
рисуется. `useIsMobile` не импортируется.

**Стартовое помещение 1×1 м** (`createRectanglePolygon(1000, 1000)`) выглядит как
настоящий расчёт.

**Стоимость не считается** — `priceUnit: unknown` в фиде. Значит блок цены в
результате должен быть спроектирован как опциональный, а не как основной.

## 2. Принятые архитектурные решения

Решения согласованы, пересмотру в ходе работ не подлежат.

**2.1. Модель высоты — контейнерная.**
Исходное ТЗ требует рабочую область высотой `calc(100dvh - header)`. Это
корректно только для отдельной полностраничной страницы: в блоке Битрикса или в
iframe `100dvh` даст обрезанный либо вылезающий за контейнер интерфейс, а
`position: sticky` будет считаться от чужого скролл-контейнера.

Принято: приложение занимает `height: 100%` от контейнера хоста с фолбэком на
`100dvh` в standalone-режиме. Все измерения рабочей области — через
`ResizeObserver` контейнера, не через `window`. Вариант работает и на отдельной
странице, и во встроенном блоке, поэтому окончательный режим встраивания на
результат не влияет.

**2.2. `optimizeLayout` удаляется.**
Функция не вызывается нигде и, по `known-limitations.md`, представляет собой
медленный перебор. Удаляется в Фазе 0 вместе с остальным мёртвым кодом. Слово
«Оптимизация» из интерфейса уходит. Если позже понадобится подбор положения с
минимумом подрезки — это отдельная задача с нормальным алгоритмом и собственным
бюджетом.

**2.3. Слой доменных событий добавляется.**
Исходное ТЗ запрещает CRM, корзину и отправку менеджеру, но без событий бизнес не
увидит, доходят ли пользователи до результата.

Принято: тонкий слой событий (выбор покрытия, ввод размеров, получение
результата, экспорт) с публикацией в `window.dataLayer` и `postMessage` наружу,
если хост слушает. Без сетевых запросов, без персональных данных, без хранения.
Ни один запрет исходного ТЗ не нарушается.

## 3. Изменения относительно исходного ТЗ

### 3.1. Порядок работ переработан

Исходный порядок — «сначала переставить экран, потом canvas, потом zoom, потом
дизайн, потом motion, потом toast, потом состояния» — приводит к тройной работе:

- каталог по §1.3 должен открываться в drawer, а Drawer как компонент появляется
  только на Этапе 5;
- загрузка текстуры по §2.1 не должна мигать, а skeleton и loading-состояния
  описаны на Этапе 7;
- дизайн-токены нужны первому же переверстанному компоненту, а вводятся на Этапе 4;
- zoom (Этап 3) переписывает ту же трансформацию, что и Этап 2.

**Новый принцип: фундамент → главная ценность → периферия → полировка.**

Порядок фаз:

| Фаза | Содержание | Соответствие исходным этапам |
|---|---|---|
| 0 | Фундамент состояния и токенов, регресс-сеть | 0, части 4.3, 15 |
| 1 | UI-примитивы, motion, обратная связь | 4.7, 4.8, 5, 6, 7 |
| 2 | Canvas как главный объект + zoom/pan + fullscreen | 2, 3, части 1 |
| 3 | Панели, каталог, помещение, результат, действия | 1, 9, 10, 11, 12, 13 |
| 4 | Планшет, мобильный, первый сценарий | 1.4, 1.5, 8 |
| 5 | Арт-дирекшен, производительность, приёмка | 4, 14, 15, 16, 17 |
| 6 | Новые функции | 18, 19, 20, 22, 23, 24, 25 |

Фазы 0–5 — это Часть I исходного ТЗ, требование «UX/UI полностью до новых
функций» сохранено.

### 3.2. Canvas поднят выше перекомпоновки панелей

Главный критерий приёмки всего проекта — «пользователь видит крупное помещение с
хорошо различимой плиткой». Это же и главный технический риск (view-модель,
retina, текстуры, производительность). Такие вещи делаются рано, пока есть запас
времени на переделку, а не после недели работы над карточками каталога.

### 3.3. Zoom/pan объединён с работой над canvas

Fit-трансформация и пользовательский zoom — одна подсистема вида. Разделять их на
два этапа нельзя.

Явно добавляю к требованиям (в исходном ТЗ отсутствует):

> Экспорт PNG и PDF и печать выгружают схему целиком в fit-виде независимо от
> текущего zoom и pan пользователя. Пользовательский вид не влияет на выгружаемый
> файл. Покрыть регрессионным тестом.

### 3.4. Доступность и производительность — сквозные, а не отдельные этапы

Исходные Этапы 14 и 15 стоят в конце. На практике a11y, доделанная в конце,
означает переписывание всех компонентов: focus trap встроен в Drawer, а не
прикручивается к нему позже.
→ Переношу их требования в Definition of Done каждой задачи (раздел 5) и
оставляю в Фазе 5 только сквозной аудит.

### 3.5. Регламент проверок сделан выполнимым

Исходное ТЗ требует после каждого этапа четыре команды и ручную проверку на
8 разрешениях по 30 сценариям. Это несколько часов ручной работы на каждый шаг —
регламент, который в реальности начнут пропускать целиком.

Заменяю на трёхуровневый:

- **после каждой задачи:** `typecheck`, `lint`, `test` + смоук на 1440, 768, 390;
- **на закрытии фазы:** плюс `build` и полная матрица разрешений и сценариев;
- **перед сдачей:** полный прогон раздела 6.

### 3.6. Добавлена регресс-сеть перед рефакторингом

В исходном ТЗ тесты стоят Этапом 24, то есть после всех изменений. Но главное
ограничение проекта — «не сломать расчёты, экспорт, каталог, сохранённые проекты».
Защищать их надо *до* рефакторинга, а не после.

Фаза 0 добавляет:

- «золотые» тесты расчёта: набор фиксированных входов (прямоугольник, Г-образная,
  П-образная, ниша, зазор, поворот 90°) с зафиксированными числами результата;
- снапшот-тест формата сохранённого проекта и загрузки проекта старой схемы;
- тест URL-предвыбора товара;
- тест разбора XML-каталога (уже есть, расширить).

Эти тесты фиксируют текущее поведение и должны оставаться зелёными весь проект.
Любое их падение — сигнал регрессии, а не повод их править.

### 3.7. Мультицвет исключён

Этап 21 исходного ТЗ (несколько цветов в одном помещении) из объёма снят.
Соответственно, из Этапа 22 убирается пункт «список цветов, если их несколько»,
из Этапа 24 — «несколько цветов».

Освободившийся бюджет направлен в Фазу 6.1–6.2 (редактор формы и препятствия),
где сейчас основная неудовлетворённая потребность пользователя.

### 3.8. Fullscreen реализуется как режим раскладки, не через Fullscreen API

Браузерный Fullscreen API на iOS Safari не работает для произвольных элементов, а
на десктопе ломает позиционирование поповеров и требует пересчёта Konva. Полезной
разницы для пользователя нет.
→ Режим «На весь экран» = раскладка, в которой рабочая область занимает весь
контейнер приложения, панели скрыты. Zoom, pan и параметры сохраняются. Выход по
`Escape` и по кнопке.

### 3.9. Стартовое состояние: не «пример», а быстрый ввод

Исходное ТЗ предлагает варианты «пример / пустое состояние / крупное уведомление».
Продуктово лучший вариант — убрать фиктивные 1×1 м и дать сразу ввести реальное:
крупное поле ширины и длины плюс несколько типовых пресетов площади в один клик.
Пользователь получает корректный результат за меньшее число действий, а ложного
расчёта не возникает вовсе.

### 3.10. Единый источник токенов

Токены объявляются в TypeScript и из них генерируются CSS-переменные. Konva
читает те же значения. Один источник правды для веб-слоя и canvas.

### 3.11. Совместимость формата проектов при новых функциях

Исходное ТЗ одновременно запрещает менять формат сохранения и требует сохранять
препятствия и проёмы. Уточняю правило:

> Схема хранения расширяется только аддитивно. `schemaVersion` повышается до 2,
> `migrateProject` дополняется восходящей миграцией. Проекты версии 1 обязаны
> открываться без потери данных. Удаление и переименование существующих полей
> запрещено. Покрыть тестом на реальном снапшоте проекта v1.

## 4. План работ

### Фаза 0. Фундамент

> **Статус: выполнено** (2026-07-29). Регресс-сеть зелёная, store разделён,
> undo/redo в store, токены — единый источник, мёртвый код удалён.

Видимых изменений интерфейса нет. Все существующие тесты остаются зелёными.

**0.1.** Регресс-сеть по разделу 3.6.

**0.2.** Разделение состояния:
- `room` — геометрия помещения (как сейчас);
- `layout` — только то, что влияет на раскладку: `rotation`, `offsetX/Y`,
  `startPoint`, `wastePercent`;
- `display` — визуальные флаги: показывать размеры, линии модулей, подрезки;
  изменение `display` **не вызывает** `recalculate`;
- `ui` — состояние интерфейса (открытые панели, режим canvas, шаг на мобильном),
  вне расчётного слоя.

**0.3.** Undo/Redo переносится в store как история изменений контура с
ограничением глубины. Начальное состояние попадает в историю. Локальный
`useState` в `RoomWorkspace` удаляется.

**0.4.** Токены: `shared/config/tokens.ts` → генерация CSS-переменных,
`KONVA_THEME` выводится из тех же токенов. Добавляются группы: поверхности,
состояния, z-index, motion (длительности и кривые), высоты контролов, focus ring.

**0.5.** Удаление мёртвого кода: `optimizeLayout`, `useIsMobile`, флаг `showGrid`
либо реализуется как настоящая сетка, либо удаляется из типов и миграции.

**Готово, когда:** расчёт не запускается при переключении визуальных флагов
(проверяется тестом), undo/redo работает из store, токены — единственный источник
цвета, регресс-тесты зелёные.

### Фаза 1. UI-фундамент

> **Статус: выполнено** (2026-07-29). Motion-хук, иконки, примитивы с a11y,
> тесты Escape/клавиатуры, документация `docs/ui-primitives.md`.
> Экраны калькулятора не менялись.

**1.1.** Motion-система: длительности и кривые в токенах, поддержка
`prefers-reduced-motion` на уровне общего хука и CSS, а не отдельных компонентов.

**1.2.** Набор иконок: tree-shakable SVG-спрайт, только используемые символы.

**1.3.** Примитивы в `shared/ui`, каждый — с доступностью внутри:
`IconButton`, `Tooltip`, `SegmentedControl`, `Switch`, `Drawer` (focus trap,
Escape, возврат фокуса, backdrop), `Popover` (позиционирование, автопревращение в
`BottomSheet` на узком экране), `Dialog`, `Toast` + провайдер с `aria-live`,
`Skeleton`, `EmptyState`, `ErrorState`.

**1.4.** Каждый примитив покрывается тестом на клавиатуру и Escape.

**Готово, когда:** примитивы существуют, задокументированы, покрыты тестами и
готовы к использованию. Экраны приложения ещё не тронуты.

### Фаза 2. Canvas как главный объект

> **Статус: выполнено** (2026-07-29). Контейнерная высота, fit/user zoom·pan,
> экспорт в fit-виде, HTML-легенда, floating toolbar, fullscreen-режим раскладки,
> текстуры без вспышки, retina pixelRatio.

**2.1.** Рабочая область получает высоту от контейнера приложения (решение 2.1),
измеряется через `ResizeObserver`, корректно работает при изменении размера окна
без скачков.

**2.2.** View-подсистема: раздельно `fitTransform` (авто) и `userTransform`
(zoom/pan). Zoom относительно курсора и центра жеста, ограничения масштаба,
«Вписать», возврат к исходному. Pan: средняя кнопка, `Space + drag`, touch drag,
отдельный режим перемещения. Разведение с перетаскиванием вершин и pinch.

**2.3.** Экспорт переводится на fit-вид (решение 3.3) + регрессионный тест.

**2.4.** Служебная графика выносится из Konva в HTML: инфо-строка, легенда,
предупреждения. Освободившаяся площадь отдаётся помещению, отступы сокращаются.

**2.5.** Текстуры: предзагрузка, плавная замена без белой вспышки, корректный
`pixelRatio` для retina, аккуратный fallback при недоступном изображении,
отсутствие повторных загрузок при перерисовке.

**2.6.** Floating toolbar: режимы, зум, вписать, полный экран, отменить, вернуть.
Иконки, tooltip, `aria-label`, горячие клавиши.

**2.7.** Режим «На весь экран» по решению 3.8.

**Готово, когда:** при типовой комнате 5×4 м на экране 1440 модуль 500×500 мм
занимает не менее 40 px, помещение — не менее 70% площади рабочей области, zoom и
pan не конфликтуют с редактированием, экспорт не зависит от вида, мерцания при
смене цвета нет.

### Фаза 3. Панели и потоки (desktop) — ✅ выполнена

**3.1.** Shell: компактная верхняя панель (бренд, имя проекта, сохранение,

## 7. Измеримые критерии приёмки Части I

Субъективные формулировки исходного ТЗ («выглядит дорого», «не как админка»)
заменены проверяемыми. Субъективный критерий приёмки означает бесконечные
переделки.

| Критерий | Порог |
|---|---|
| Доля ширины под рабочую область на 1440 | ≥ 65% |
| Доля площади рабочей области под помещением при fit | ≥ 70% |
| Размер модуля 500×500 мм на экране (комната 5×4 м, 1440) | ≥ 40 px |
| Время до первого корректного результата, новый пользователь | ≤ 4 действия |
| Ошибок в консоли за полный сценарий | 0 |
| Сдвиг раскладки при загрузке каталога и изображений | отсутствует |
| Пересчётов геометрии при переключении визуального флага | 0 |
| Перезагрузок текстуры при переключении мобильного шага | 0 |
| Контраст текста | WCAG AA |
| Регресс-тесты Фазы 0 | все зелёные |
| Отдельный раздел «Раскладка» в интерфейсе | отсутствует |
